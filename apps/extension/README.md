# Gunda Capture (browser extension)

Reports the media a page plays to the Gunda desktop application, over a loopback
WebSocket. This is the browser half of the capture channel documented in
[`docs/design/media-capture.md`](../../docs/design/media-capture.md); the desktop
half is the `gunda-capture` crate.

## What it reports

Two sources, because neither is enough on its own:

| Source | File | Sees |
| --- | --- | --- |
| Response sniffing | `background.js` | every response the browser fetches, including the manifests and media files that Media Source Extensions hide from the page |
| DOM scanning | `content.js` | `<video>`, `<audio>`, and `<source>` elements the page declares, including ones a page builds from data it already had |

A report is `{ url, content_type, page_url, page_title }`. It contains no
cookies, no request headers, and no page content, so a captured download carries
none of the browser's session with it.

Stream segments (`video/mp2t`, `.ts`, `.m4s`) are deliberately **not** reported:
the manifest is the resource worth downloading, and a segment is not a
downloadable presentation.

## Installing it

Chrome and Edge (a Chromium build; Firefox would need a `background.scripts`
manifest variant, which does not exist yet):

1. Open `chrome://extensions`.
2. Turn on **Developer mode**.
3. Choose **Load unpacked** and select this directory (`apps/extension`).

## Pairing

1. Start the Gunda desktop application; its capture panel shows an endpoint such
   as `ws://127.0.0.1:49152/capture` and a 64-character token.
2. Open the extension's options (Details > Extension options) and paste both.
3. **Save and connect.** The status line reports `connected` once the greeting is
   accepted.

The token is generated by the desktop on first run and stored next to its other
application data. It is what stops a page in this browser -- which can reach
`127.0.0.1` just as easily as the extension can -- from injecting downloads. The
endpoint also refuses connections whose `Origin` is not an extension origin, so
removing the token would still not make a web page able to report.

## Why these permissions

| Permission | Why |
| --- | --- |
| `webRequest` | to observe responses and read their content type. Nothing is blocked or modified |
| `host_permissions: <all_urls>` | a capture can be on any site; response headers are not readable without it |
| `tabs` | to name the page a capture came from. Only the URL and title of the tab that made the request are read, and only to attribute the capture |
| `storage` | to remember the pairing, and to hold the status shown in the options page |
| `alarms` | a service worker is suspended when idle, and the alarm is what brings the channel back |

## Limits, stated plainly

- A report made while the desktop app is not running is held in the worker's
  memory and sent when the channel connects. If the worker is torn down first,
  the report is lost; the page can be played again.
- Only `http` and `https` pages are attributed. A capture from a page with no
  such URL is dropped rather than attributed to the wrong place.
- The desktop decides what is downloadable. A refusal comes back as a stable
  reason (`unsupported_url`, `unsupported_media`, `segment_stream`,
  `unsupported_version`) and is counted in the options page.
- Paired to two browsers at once, both connect; the desktop deduplicates by media
  URL.
